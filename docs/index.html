Abstract

Our independent Rust engine and distributed negamax search establish that perfect play from the standard initial position of DOSELLO gives Black a final disc difference of +2. The optimal openings are f3-f4 and its 180° rotational counterpart c5-c6. The 758-position certificate stores 456 endgame search jobs; legal transitions and interval propagation have been checked. “Solved” refers to the standard initial position, not every reachable position.

We combine exact and null-window bound searches, totaling 6.736 trillion searched nodes. The independent engine, sanitized proof archive, consistency checker and original WebAssembly interface are included. The checker validates legal transitions and interval propagation but trusts saved solver results rather than independently re-solving the leaves.

Initial value: Black +2

1. Introduction

The original DOSELLO — an Othello variant is a third-party game. This research independently implements its rules. Original JavaScript, HTML, CSS, images and favicon are not distributed here.

The board has 8×8 cells, initially four discs of each color arranged as four dominoes. Each move places a same-color domino in two orthogonally adjacent empty cells. As in Othello, opposing discs are captured along straight lines in eight directions. Each directly captured disc’s partner also flips. Partner flips do not trigger further captures. A legal move must directly capture at least one disc.

A player without a legal move passes; play ends when neither player can move. The score is Black discs minus White discs on the board. Empty cells are not awarded to the winner. A position includes domino pairing as well as disc colors.

2. Game size & comparison with Othello

The initial 56 empty cells allow at most 28 placements, excluding passes. We measured 100,000 games with a fixed seed and uniform legal-move selection using the independent Rust move generator. The mean length was 24.86827 placements. Early mean branching factors were 20.00, 12.70, 14.33, 13.13, 15.07, 14.98, 14.99, 15.28, 14.61, 14.92, 13.86, 13.98 and 12.75.

3. Engine

The Rust engine uses only the standard library. Position keys consist of four 64-bit boards—Black, White, horizontal domino left ends and vertical domino top ends—plus side to move. Bit operations implement two-cell placement, directional captures and partner flips. An independent JavaScript rules implementation supports cross-checking WASM output.

Midgame search uses iterative deepening, PVS and 16-byte transposition entries. The current evaluator, eval3, is an independent linear pattern model: 32 instances of 6-cell patterns, with five cell states encoding color and domino orientation, incremental pattern-state updates, and cheap global terms. It uses the trained eval3-r2.bin weights. Plain eval3 is the chosen configuration: ProbCut and eval-guided move ordering were tested but not adopted because they gave no gain at equal time. Endgame proofs continue to separate heuristic estimates from exhaustive bounds.

Training used 5,999,964 exact labels (22–34 empties) plus approximately 150,000 deep-search labels (36–54 empties): 20 seconds per position at 36–44 empties and 5 seconds at 46–54. Local holdout measurements against exact labels reduced static MAE from 15.8 to 10.9 discs at 30–32 empties and from 14.3 to 10.4 at 34–36. Local search benchmarks measured 2.8–8.5× the speed of the previous learned evaluator; the ratio depends on the position and benchmark conditions. Inference weights are included, but the full training data and journals are not. These are source-project measurements, not experiments rerun for this release.

Parallel search follows the Young Brothers Wait Concept (YBWC): search the first sibling before processing the rest in parallel. Prior measurements reported about 3.7–3.8× speedup at 14 threads, depending on position and load. A representative exact-search position reached about 10.6M nodes/s on one Apple M4 thread. These are prior benchmark reports, not the average speed of the certificate computation.

The same Rust source builds for wasm32-unknown-unknown and analyzes in a browser Worker. Shared memory and special HTTP headers are unnecessary. The Worker loads approximately 1.9 MB of eval3 weights and the TOOL and DISPLAY books (approximately 2.62 MB combined); large sharded books are excluded. If weight loading fails, it quietly retains the previous evaluator. The analyzer distinguishes proven values and bounds from time-limited estimates.

4. Proof method

For side-to-move value V, negamax gives V(s) = maxm −V(s·m). Child intervals [Li, Ui] propagate to [max(−Ui), max(−Li)]. We solve the most promising move exactly and use null-window searches to show that alternatives cannot exceed it. Exact values for every move are unnecessary.

The coordinator advances a best-first proof and uses idle slots for speculative candidates. Long jobs split into child positions. All jobs in this saved certificate start three placements from the initial position, with 50 empty cells. Symmetric positions share bounds, which propagate upward.

The coordinator schedules work; remote workers search over SSH. Checkpoints, atomic state saves, job identifiers and retries support resumption. Small local tests exercise recovery and injected failures. Published host settings contain generic host-a/b/c examples only. No SSH or distributed search was started during this revision.

7. Verification & limitations

proof/verify.py uses Rust job --type inspect to enumerate legal moves and compare all saved children and symmetric transitions. It checks job position IDs, types, thresholds and intervals, then reconstructs every interval by repeated negamax propagation from terminal values and saved job intervals. It verifies root [2,2], both optimal openings, the reply table and the first three PV moves.

Verification limits: saved exhaustive leaf results are trusted outputs of this engine; the leaves are not independently re-solved here. Legal-move checks also use the same Rust rules, so this is not an independent third-party proof. There are 374 unsearched leaves with interval [−64,64]; interval propagation confirms they do not affect the root result.

Raw job results are included in proof/initial-proof.json. Host identities were replaced with generic names for privacy, changing the SHA-256 relative to the original archive. Position IDs, intervals, nodes and timestamps are preserved. The verification report records the public file’s hash. Full visited-position traces, large book journals and full training data are excluded.

The analyzer’s estimates do not guarantee perfect play. Outside the book it uses time-limited search. Game-size sampling estimates and cross-machine speed comparisons also depend on their experimental conditions.

8. Playing strength

In local equal-time, paired-color matches without an opening book, plain eval3 scored the following results against the previous AI (400 games per time budget, four random opening plies). Score counts a draw as half a win. These source-project measurements were supplied for this release; timing and random openings affect the results.

Time per move, both AIsWins–draws–lossesScore
100 ms243–11–14662.1%

3000 ms215–16–16955.8%

Against the original site’s level-5 CPU, eval3 at 500 ms/move recorded 397 wins, 0 draws and 3 losses in 400 games. The experiment owner reports that all three losses were decided by the random opening plies before the AI moved or arose from an already lost position. The opponent was a source-project reimplementation cross-checked against the original CPU; it is not bundled here. The site CPU uses fixed-depth search, so this comparison is not equal-time.

On the solved suite (300 positions per phase), local equal-time best-move accuracy at 3 seconds per position improved from 97% to 99% at 30 empties, 73% to 82% at 34 empties, and 65% to 76% at 38 empties (previous AI → eval3). ProbCut and eval-guided ordering were also tested and not adopted: neither improved equal-time performance. Match results and move accuracy do not establish the initial-position proof.

The analyzer demo remains a time-limited search, not a perfect player. Proven best moves from the bundled book take priority; elsewhere the AI searches for 3000 ms per move and can choose non-optimal moves. Browser speed limits exact endgame solving. The solved value (+2 for Black) rests on the proof in Sections 4–7, not on demo play.

Reproducibility

Run from the repository root with Rust, Python 3 and Node.js 22 or newer. There are no external Rust crates or npm dependencies.

export CARGO_TARGET_DIR="$PWD/rust/target"
cargo build --release --offline --manifest-path rust/Cargo.toml
cargo test --release --offline --manifest-path rust/Cargo.toml
DOSELLO_OFFLINE=1 npm test
python3 proof/verify.py
rust/target/release/game_stats 100000 5
python3 proof/summarize.py
(cd docs && python3 -m http.server 8000 --bind ::1)

To run locally, open http://localhost:8000/ and /play/. Rebuild WASM with bash rust/tools/build-wasm.sh using an installed wasm32-unknown-unknown target. The published site is wand125.github.io/solving-dosello/.

Users who permit network access can explicitly run DOSELLO_OFFLINE=0 bash rust/tools/crosscheck.sh for optional original-game comparison. Original code is downloaded only into an ignored cache, and unavailable downloads result in SKIP. See README for distributed solving and generic host settings.
